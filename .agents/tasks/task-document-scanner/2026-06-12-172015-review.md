# CamScanner-like document scanner page for mobile CRM

A new standalone page (`/scanner.html`) adds mobile-first document scanning to the CRM: search for a customer, capture multiple photos via the device camera, enhance images with brightness/contrast/sharpen/auto-enhance/rotate, generate a multi-page PDF client-side via jsPDF, and upload it to the customer record. The backend gains a single new endpoint (`POST /api/customers/:id/upload-scanned/:docType`) that reuses the existing custom multipart parser and saves to the same file structure as the original upload routes.

**Watch for:** The "Reset" button cannot actually undo sharpen or rotate operations because those overwrite the original data URL (confirmed). Camera stream is not stopped on page navigation or browser back button — only explicit user action stops it (confirmed). The search endpoint returns the full customer list unfiltered when the query is under 2 characters, which could expose data if bookmarked (likely). The upload endpoint skips the `.pdf` extension check that exists on the sibling `upload-agreement`/`upload-receipt` routes (confirmed).

## High-level view

The scanner page implements a three-step wizard (select customer, capture via camera, review/enhance and upload) with all image processing on a shared `<canvas>` and PDF assembly happening entirely in the browser via jsPDF. The backend endpoint is a near-duplicate of the existing upload routes with a dynamic docType parameter, avoiding new dependencies.

Image enhancement operations (sharpen, rotate) permanently mutate the `original` field in the page state array, so "Reset" only reverts brightness/contrast sliders — not the destructive transforms. The upload endpoint drops the `.pdf` extension validation present on the sibling routes, allowing arbitrary binary to be written to disk if called directly.

<summary>Issues (5)</summary>

1. **Destructive enhancement overwrites original** — `sharpen()` and `rotateImage()` set `pages[i].original = pages[i].enhanced`, making "Reset" unable to recover the captured photo. Store the untouched capture separately from the working copy.
2. **Missing `.pdf` extension check on scanned upload** — The `upload-scanned/:docType` endpoint omits the `filename.toLowerCase().endsWith('.pdf')` guard present on `upload-agreement` and `upload-receipt`. Add the same check for parity.
3. **Camera stream leaks on navigation** — If the user presses the browser back button or navigates away while the camera is open, `cameraStream.getTracks()` are never stopped. Add a `beforeunload` or `pagehide` listener to release the stream.
4. **XSS in customer search results** — `selectCustomer` passes `JSON.stringify(c)` into an inline `onclick` attribute with only `"` → `&quot;` escaping. A customer name containing a single quote and closing paren breaks the HTML attribute. Use event delegation or data attributes instead of inline handlers with interpolated JSON.
5. **No debounce protection on PDF upload** — The "Create PDF & Upload" button is never disabled during the upload operation, so rapid double-taps can trigger parallel uploads of the same document.

<summary>Details</summary>

## Destructive enhancement pipeline

The `pages` array stores `{ original, enhanced, rotation }` per captured photo. Both `sharpen()` and `rotateImage()` overwrite `original` with the transformed result:

```javascript
// In sharpen():
pages[selectedPageIndex].original = pages[selectedPageIndex].enhanced; // Make sharpen cumulative

// In rotateImage():
pages[selectedPageIndex].original = dataURL;
```

After one sharpen or rotate, `resetEnhance()` can only revert brightness/contrast back to the already-sharpened/rotated version — it resets sliders and calls `drawEnhanced(selectedPageIndex)` which loads from `.enhanced`, never from a pristine source. The comment "Make sharpen cumulative" suggests this was intentional for stacking, but it breaks the user's expectation that "Reset" means "undo all edits."

Fix: add a `captured` field that never gets overwritten, and have `resetEnhance()` restore from `captured`.

## Camera stream leak on navigation

The only paths that call `stopCamera()` are the close button and the "Done" button in the camera overlay. If the user navigates away (back button, URL bar, or page refresh), the stream leaks until the browser's garbage collector catches it — which on some Android WebViews means the camera LED stays on indefinitely.

Adding a `pagehide` or `visibilitychange` listener that calls `stopCamera()` covers the common leak paths.

## XSS vector in search result rendering

The search results interpolate `JSON.stringify(c)` into an inline `onclick` attribute:

```javascript
results.innerHTML = customers.map(c => `
  <div class="search-result-item" onclick="selectCustomer(${JSON.stringify(c).replace(/"/g, '&quot;')})">
```

The `replace` handles double quotes, but a customer name containing `</div>` or characters that break HTML attribute parsing can inject markup. Since this is an internal CRM where staff enter data, exploitation requires a malicious data entry — low probability but easy to fix with event delegation or a click handler that looks up the customer by array index.

## Upload endpoint missing file-type validation

The existing `upload-agreement` and `upload-receipt` endpoints both enforce:
```javascript
if (!filename.toLowerCase().endsWith('.pdf')) {
  return res.status(400).json({ error: 'Only PDF files are allowed' });
}
```

The new `upload-scanned/:docType` endpoint skips this check. The client always sends a `.pdf` filename, but the endpoint is publicly accessible — any HTTP client can POST arbitrary binary that gets saved with a `.pdf` extension. Adding the same guard (or a `%PDF-` magic-byte check) brings it in line with existing routes.

## Double-tap race on upload

`createPdfAndUpload()` shows the overlay spinner but never disables the button or sets a guard flag. The overlay's CSS opacity transition takes ~300ms to fully cover the button; a fast double-tap before the overlay appears triggers parallel PDF construction and upload. The practical damage is limited to double network traffic and a confused UI state, but adding `document.getElementById('upload-btn').disabled = true` at the top of the function eliminates it.
